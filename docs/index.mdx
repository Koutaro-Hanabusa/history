# 英 洸太朗（Hanabusa Koutaro）

最終更新: 2026 年 8 月 12 日

## 職務要約

React / TypeScript を軸とするフロントエンドエンジニア。幼保関連業界向けに、社内・園の先生・カメラマンといった、業務のなかで毎日その画面を使う人が触れるプロダクトを担当。

要望をそのまま実装するのではなく、使う人がどこで手を止めているかを起点に課題を定義し、画面の設計・実装で解消することを一貫して重視。フロントエンドで閉じない課題には Laravel / Go によるバックエンド改修や API 設計まで踏み込み、FE / BE をまたいで解決できる点が強み。あわせて、変更を安全に届け続けるための開発基盤・品質基盤の整備にも取り組む。

## 開発経歴

### 2025 年 5 月〜2025 年 11 月 社内向け・先生向け管理画面の改善

- メンバー / プロジェクト規模: 5〜10 人
- PHP / Go / TypeScript / Laravel / React
- 要件定義、仕様設計、コーディング、レビューを担当

#### 管理画面の改善

- 社内オペレーション向け・先生向けの 2 系統の管理画面（React + Laravel / React + Go）を改善
- フロントエンドを主軸に、FE / BE が連動する改修を担当

#### 申し込みフローの改善

- 申し込みフローの画面をリプレイスし、社内オペレーションの工数と顧客側の入力ミスを削減
- 編集機能を追加し、申し込みのやり直しにかかるコストを解消
- 入力量の多いタイムスケジュール登録はフォームを分割し、前年度の登録内容を参照できるようにして入力負荷を軽減
- 申し込んだ撮影内容の詳細閲覧機能を、イベント種別に対応する形で実装。OpenAPI でスキーマを定義し、フロントエンドとバックエンドを一貫して担当

#### 描画パフォーマンスの課題提起

- 一覧画面の描画が遅い原因を調査し、コード分割・ルーターのプリフェッチの見直しを改善案としてチームへ提案
- 実装には至らなかったものの、フロントエンドの基盤改善に取り組むきっかけとなり、次のプロジェクトでのバージョン更新・ツールチェーン整備に着手

#### デザインシステム

- β 版デザインシステムを構築し、既存画面のコンポーネント置き換えにも適用。後の全社デザインシステムの土台へ

### 2025 年 10 月〜2026 年 2 月 業務ツールの Web 化プロジェクト

- メンバー / プロジェクト規模: 5〜10 人
- PHP / TypeScript / Laravel / React
- 要件定義、仕様設計、コーディング、レビュー、テスト・QA を担当

#### 写真検査・納品ツールの Web 化

- カメラマンが大量の写真を検査・納品するデスクトップツールの Web 化プロジェクトに、フロントエンドエンジニアとして参画
- フロントエンドの体制が限られるなか、機能実装と並行して開発基盤・品質基準の整備を推進

#### 開発基盤・品質改善

- 機能実装に先立ち、ライブラリ更新・テスト・Lint 環境を整備し、技術的負債を解消
  - [プロダクトブログ](https://productblog.sencorp.co.jp/entry/2025/12/15/100000)
- Node.js / Vite のバージョン更新では、QA が管理する機能一覧をもとに不具合発生時の事業影響で優先度を付け、擬似 CUJ を作成して検証。リリース前に不具合 3 件（メンテナンスが終了した UI ライブラリに起因）を検出・解消し、ユーザーへの影響を未然に防止
- Lint 導入で顕在化した `autofocus` 属性を含むアクセシビリティ上の問題を解消
  - [autofocus 属性のアクセシビリティを扱った発表スライド](https://slide.burio16.com/autofocus-correct-usage)（社内 LT 会 / Frontend Conference Nagoya 2026 前夜祭）
- MUI から Tailwind CSS への部分移行を提案・実施し、段階的な移行方針を策定
- 導入の判断理由と適用範囲は ADR として残し、ESLint / Prettier の設定を追加して記述の揺れを防止
- ESLint に a11y ルール、textlint に UI 文言のルールを追加し、アクセシビリティと文言の問題を機械的に検出できる状態を整備

#### 写真バリデーションの再設計

- 写真バリデーションの Zod によるスキーマベース化を、技術検証から実装まで担当
- 業務ドメイン固有の例外パターンに対応しつつ、既存仕様を変えずに型安全性・保守性を改善
- JPEG のヘッダー部分のみを段階的に読み込み、Exif の解釈は ExifReader に委譲する方式と、検査処理の並列実行を組み合わせ、バリデーションの所要時間（2500 枚想定）を 489,173ms から 4,134ms へ短縮し、納品フロー全体の高速化に寄与
- 一連の改善を含む Web 化プロジェクトの取り組みでチーム表彰を受賞

#### テストと段階的リリース

- 処理の大半がフロントエンドで完結する構成のため、バリデーションとロジックを対象にテストを整備し、動作を保証できる範囲を明確化
- 社内向けの先行公開期間を設け、フィードバックを取り込みながら段階的にリリースする計画を設計
- 先行公開では納品を止める重大な不具合は発生せず、寄せられたフィードバックには仕様の代替案を先回りして提示。優先度の高い改善は翌日リリースまで含めて主導

#### 旧ツールの撤去

- Web 版への移行後、旧 Electron 製デスクトップツール向けの API・アップロード機能・画面導線を撤去し、移行の完了まで担当
- 廃止に伴う案内メールの文面変更もあわせて対応し、旧経路が残らない状態へ

### 2025 年 10 月〜 EC サービスの運用保守（開発と並行）

- メンバー / プロジェクト規模: 5〜10 人
- 障害の一次対応、問い合わせ対応、運用フローの整備を担当

- 決済代行サービスからの通知を内容に応じて判断し、緊急度に沿って担当チームへエスカレーション
- 通知メールの受信を Zapier で Slack へ連携し、異常に気づくまでの時間を短縮
- 決済まわりの問い合わせ手順をドキュメント化し、初めて対応するチームには同席してサポート

#### 運用範囲の整理

- 所管が曖昧なまま滞留していた問い合わせを、関連チームと調整のうえ自チームで対応できる体制へ変更
- 開発経験のない領域の仕様調査では、AI エージェントを用いてコードから仕様を洗い出し、チームで裏付けを取って回答
- 対応した内容はその都度ドキュメント化し、体制が変わっても引き継げる状態を維持

### 2026 年 2 月〜現在 全社共通デザインシステムの構築

- メンバー / プロジェクト規模: 1〜10 人
- TypeScript / React / Tailwind CSS / Vite / Vitest / Astro / Cloudflare
- コンポーネントの設計・実装、VRT / CI/CD 基盤の構築、ツールチェーンの整備、AI 連携基盤の実装を担当

#### 背景

- 社内に複数のプロダクトがあるものの、トーンが揃わずブランドの一貫性を欠いていた。全社リプレイス計画を契機に、共通デザインシステムをゼロから構築するプロジェクトが発足

## 自己 PR

社内にフロントエンド専任のエンジニアがいない環境で、使う人の課題を実装で解決しながら、フロントエンドの標準をつくる側に回ってきました。目の前の画面をよくすることと、次に誰かが同じ問題に当たらない状態をつくることの両方を、自分の担当領域だと考えています。

#### 新しい技術の検証・導入

- フロントエンドのみで 1 プロダクトを構築する PoC で技術選定を担当し、TanStack Router / TanStack Start の導入を決定
- 事例が少ない技術でも、ディレクトリ構成・ルーティングの責務・運用方法を技術検証し、長期運用を見据えたアーキテクチャへ落とし込み
  - [TanStack Router / Start の技術選定とディレクトリ構成に関する発表スライド](https://slide.burio16.com/tanstack-router-dir-structure)
- PoC の進行中に認証などサーバー側での処理が必要になった時点で TanStack Start への移行を判断。サーバー関数の責務と配置ルールもあわせて ADR として明文化し、判断の経緯が後から追える状態を維持
- 実装者ではない立場でも、今後保守する前提でアーキテクチャとディレクトリ構成の意思決定を担当。基盤が定まらないまま開発が複雑化することを避けるため、着手前に方針を固めることを重視

#### 品質基盤とアーキテクチャの実装

- 設計方針を bulletproof-react ベースに定め、routes / features のレイヤ分離を Lint で強制。ルーターへの依存が機能側へ染み出さない構造を維持
- 12 のドメインすべてにテストを整備。ページ単位の UI テストは Playwright Test + Docker で実行する構成に刷新し、MSW でのモックとあわせて画面の動作を継続的に検証できる状態に
- staging から main へのリリース PR 自動生成、依存更新の自動マージ、AI レビューの導入により、リリースと保守にかかる手作業を削減

### デザインシステムの構築と展開

管理画面の改善プロジェクトで構築した β 版デザインシステムが、全社デザインシステムの土台として採用されました。現在は全社共通デザインシステムの新規構築にフロントエンドとして参加しています。作ることだけでなく、利用者が正しく継続的に使える状態をつくることを重視しています。

#### コンポーネント・品質基盤

- コンポーネントの設計・実装に加え、カタログ、VRT、CI/CD、Figma Code Connect を整備し、複数プロダクトで安心して変更・利用できる品質基盤を構築
- フォーム・ダイアログ・テーブル・ナビゲーションなど 40 種類以上のコンポーネントで構成されるライブラリを、チームで分担して設計・実装。基盤 / 業務向け / 設定 / Lint / MCP / カタログをパッケージとして分割し、changeset でバージョン管理と配布を運用
- アクセシビリティは個別対応にせず、focus-ring をトークンとして定義して全コンポーネントの focus-visible を統一。検索欄を WAI-ARIA の combobox パターンへ整理するなど、キーボード操作と支援技術への対応を横断的に改善
- VRT は、ベースライン画像を Git 管理せず、main ブランチのコードから再生成可能な CI キャッシュとして扱う運用を設計。Playwright + Docker で実行し、スナップショットは Cloudflare R2 に保存。PR 上で Before / After / Diff を確認し、意図した変更だけを更新できるレビュー体験を整備
- カタログは Astro で構築して Cloudflare Pages へ配信。各コンポーネントに使い分けの基準とアクセシビリティ上の注意点を記載し、実装者が判断に迷わない状態を整備
- Figma 仕様と実装・カタログ・Code Connect の同期を行い、デザインと実装の乖離を防ぐ運用を推進
- デザインシステム固有の Lint ルールを実装し、利用ルールから外れるコードを開発時・CI で検出できる状態を整備
- チームでベース部分を構築したうえで、各プロダクトの PoC で必要になったパーツを随時共有・レビューして本体へ統合する体制を構築し、設計の一貫性を担保
- 各所で並行して実装が進むサイロ化とタスク漏れを防ぐため、タスクの棚卸しと進捗確認の場を設計・運用

#### 開発基盤・アーキテクチャ

- Vite+ を中心に、lint / format / test / タスク実行 / Git hooks を統合。タスク間の依存関係とキャッシュを明示し、継続的に開発・配布できるツールチェーンへ刷新
  - [Vite+ 導入とツールチェーン統合に関する発表スライド](https://slide.burio16.com/vite-plus-retro)（Vue Fes Japan 2026 採択）
- ライブラリとして配信する要件を踏まえ、Lint / Format には Oxlint / Oxfmt を採用。ビルドの成立を前提条件として整理したうえで、モダンなツールチェーンへ寄せる判断を実施

#### AI 駆動開発への展開

- デザインシステムの MCP サーバーと Skills を実装し、AI エージェントが最新のコンポーネント仕様・具体的な使用方法・禁止事項を参照して正しく実装できる環境を整備。ビルド時に最新のデザインシステムを取り込む構成とし、仕様が更新されても参照先が古くならない状態を維持
- Nix の devShell と direnv で開発環境を再現可能にし、環境構築の障壁を低減。README の手順どおりに進めれば構築が完結する状態をつくり、誰が開発に加わってもよい状態へ
- デザインツール側の利用枠に依存せずデザインシステムを試せるよう、React でプロトタイプを作成できるツールを構築。デザイナーが Figma Dev Mode MCP・AI エージェント・社内デザインシステムを組み合わせて検証できる環境を整備
  - [Frontend Conference Kansai 2026 採択 LT「AI時代に、みんなでフロントを作るためのNix」](https://fortee.jp/fec-kansai-2026/proposal/03c1cdcf-5644-420d-bf67-5037bd6af6a5)

## 今後の展望

### フロントエンドを軸足に、フルスタックに動けるエンジニアへ

これまでも画面の実装だけで完結したことはなく、Laravel / Go での API 設計・バックエンド改修、VRT や CI/CD・プレビューデプロイ基盤の整備、Cloudflare での配信構成まで、プロダクトを前に進めるために必要なレイヤーは自分で触ってきました。フロントエンドは画面を作るだけの仕事ではなく、プロダクト体験・開発体験・品質・運用のすべてを設計する領域だという実感があります。今後も軸足はフロントエンドに置きながら、その前後にある API 設計・インフラ・開発基盤まで責任を持てる範囲を広げ、フロントから入ってプロダクト全体を動かせるエンジニアになりたいと考えています。

### 業界に向けた発信を続ける

これまでは社内に閉じた形でプロジェクトに関わってきましたが、業界全体に対してアウトプットする側に回りたい気持ちが強くなっています。カンファレンスでの登壇や技術イベントの開催・運営を通じて、自分の経験を外に還元しながら、業界とつながる動き方を続けていきます。

### 人の「感情」を支えるものづくりに携わる

恩師から言われた「人間の感情はデジタル化できない」という言葉が、ずっと残っています。AI が多くの仕事を代替していく時代に、それでも置き換えられないのは、人が何かを「好き」になったり「ありがたい」と感じたりする熱量だと考えています。デジタル化できないからこそ、その感情が生まれる瞬間を支えるプロダクトには、人の手で設計し続ける価値がある。そしてそれを人に見える形にするのがフロントエンドという職種だと捉えています。

自分自身、海外サッカーに熱中したり、オタクとしてのめり込んだりしてきました。何かを心から好きになり、その対象に時間やお金や感情を注ぐ体験は、日常を前向きにしてくれる特別な力を持っていると実感しています。そしてそうした体験は、裏側でそれを支えるプロダクトや仕組みがあって初めて成立します。業界そのものを限定するのではなく、人がデジタルの向こう側で何かに夢中になっているとき、その体験を地味にでも確実に支えている基盤に関わるエンジニアでありたいと考えています。
